# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- `Demolition Men/` — the Unity project (Unity **6000.6.7f1**, 2D, built-in render pipeline). All code lives under `Demolition Men/Assets/`.
- `docs/building-destruction-design.md` — design rationale for the destruction system ("Option C" support-graph), the NGO (Netcode for GameObjects) networking plan, and the PlayMode manual test checklist.
- `docs/roadmap.md` — the plan to v1.0, the Google Play release in January 2027: what's built and what's left, milestones M0–M6 (built) and the release milestones R1–R5, the procedural building/level generation design, the art pipeline and the agentic content pipeline, plus the design decisions. Check it before starting feature work.
- `docs/marketing.md` — reaching players on a €100–500 budget: audience, clips and the clip mode, free channels, the paid launch push, the calendar to launch, what to measure.
- `docs/multiplayer.md` — the online co-op plan: player-hosted NGO over a self-hosted WebSocket relay on the VPS (no game server, no paid services, works in WebGL), who decides what, every message and its size, milestones O1–O5, what the VPS is for.
- `docs/ranked.md` — ranked dailies (a solo and a co-op board, no upgrades) and why their scores are real: the device logs the run, our server replays the log with the game's own models and scores it; the log format, every check, sealing the log, the server, milestones K1–K6.
- `docs/rendering.md` — URP 2D: what the lighting code does, the one-time editor steps (install URP, the 2D pipeline asset, the converter), what to check.
- `docs/store-media.md` — store screenshots, the trailer and clips: what we show, the shot list, recording by script from the editor (Clip Lab, shot files, `tools/media/`), the phone takes, and what else Play and the first ads need.
- `docs/monetization.md` — the ads seam (free game with ads on phones), placements, wiring AdMob with UMP consent, store/consent checklist.
- `tools/unity-check/` — compile-check and model tests without the Unity editor (see Commands).
- `tools/media/media.py` — Python + ffmpeg for the Clip Lab's takes: crops (9:16, 16:9, 1:1), highlight cuts from a take's event log, contact sheets, GIFs, captioned store screenshots and ads images, Shorts and the trailer from cut lists (`content-work/edits/*.json`). Shot files are `content-work/shots/*.json`; recordings go to `content-work/media/` (gitignored).
- `server/ranked/` — the ranked boards' server for the VPS (ASP.NET Core, .NET 10, SQLite): it compiles the game's `*/Model/` code with the unity-check shim and ships the campaign's JSON, so it replays run logs with the game's rules (`docs/ranked.md`). `dotnet test Ranked.Tests`; `deploy/deploy.sh <ssh-target> <domain>`; see its README (API, settings, review with the admin token).
- `server/relay/` — the online co-op WebSocket relay for the VPS (ASP.NET Core, .NET 10, no game code) with its tests (`dotnet test Relay.Tests`) and `deploy/deploy.sh <ssh-target> <domain>`; see its README.
- The `*.csproj` / `*.slnx` files and `Library/`, `Temp/`, `Logs/`, `UserSettings/` are Unity-generated or per-user and gitignored. Unity regenerates `Demolition Men.slnx` (the four project assemblies) when the editor opens the project.

## Commands

All paths below are relative to the repo root.

**Without the editor (cloud agents, CI, Linux):** `tools/unity-check/setup.sh` once, then
```
tools/unity-check/check.sh          # compile all assemblies + run the EditMode model tests
tools/unity-check/check.sh build    # compile only
tools/unity-check/check.sh test -- --where "class == Demolition.Tests.MetaTests"
tools/unity-check/refs.py --since <rev>   # hand-edited scenes/prefabs/assets: unresolved GUIDs, dangling fileIDs
tools/unity-check/check.sh levels && python3 tools/artpipe/level_preview.py   # every level drawn with its theme's art: content-work/levels/*.png
```
It compiles `Demolition`, `Demolition.Online` (`Online/Controller/`, its own asmdef), `Assembly-CSharp`, `Assets/Editor` (against an older UnityEditor.dll, so a brand-new editor API can false-fail), the `Demolition` assembly with `UNITY_EDITOR` defined, the PlayMode tests, the EditMode tests (compile only: the test run below uses the shim, which lacks most of UnityEngine, so a name both define, such as `Pose`, only clashes here), the Clip Lab (`Assets/Editor/Clips`, its own asmdef, against `RecorderStubs.cs`: add any Recorder member you use there, copied from the package's `Editor/Unity.Recorder.Editor.api`), `Demolition.Ads.UnityIap` against `IapStubs.cs` (Unity IAP 5.4.4 signatures: likewise), against Unity 6000.4 reference assemblies; then runs the EditMode tests on plain .NET with `UnityShim.cs` standing in for the UnityEngine value types. Only code under `*/Model/` (minus `Session.cs`) is in the test build, so models must not touch scenes, MonoBehaviours or devices. The registry's uGUI it compiles renamed `TMP_FontAsset`; `TmpCompat.cs` puts the editor-bundled name back (compile only). Netcode for GameObjects 2.13.3 (with Transport, Collections, Burst, Mathematics) and NativeWebSocket are built from source too, unpatched; package versions and the defines mirrored from each asmdef live in `setup.sh` and `projects/*.csproj`. New `.cs` files are picked up automatically (globs), but **every new asset needs its `.meta`** — Unity is not there to make one.

**Compile check (fast, works while the editor is open):**
```
dotnet build "Demolition Men/Demolition Men.slnx"
```
The generated csproj files list sources explicitly (`<Compile Include>`), so a newly created `.cs` file is not compiled by this until Unity regenerates the projects (focus the editor, or Preferences ▸ External Tools ▸ Regenerate project files). Output goes to `Temp/obj`.

**EditMode tests** (`Assets/Tests/EditMode/`, assembly `Demolition.Tests.EditMode`: `BuildingStructure`, `RunState`, `RunScore`, building and level generation, meta/ads/input models):
- With the editor open: Window ▸ General ▸ Test Runner ▸ EditMode ▸ Run All. Batch mode refuses to run while the editor holds `Temp/UnityLockfile`. From an agent, the Unity MCP `RunCommand` can start `TestRunnerApi` with an `ICallbacks` that writes results to `Temp/` (the callback class must be top-level, not nested; `System.Reflection` is blocked).
- With the editor closed (PowerShell):
  ```
  & "C:\Program Files\Unity\Hub\Editor\6000.6.7f1\Editor\Unity.exe" -batchmode -projectPath "Demolition Men" -runTests -testPlatform EditMode -testResults "$env:TEMP\editmode.xml" -logFile -
  ```
  Single test: add `-testFilter "Demolition.Tests.BuildingStructureTests.RemoveMidColumn_DetachesEverythingAbove"`. Don't pass `-quit` with `-runTests`.

**Android build:** Tools ▸ Demolition ▸ Build ▸ Android AAB (release / development), or batch `-buildTarget Android -executeMethod AndroidBuild.ReleaseCli` (`Assets/Editor/Android/AndroidBuild.cs`): raises the versionCode, writes `Builds/Android/DemolitionMen-<version>-<code>.aab`, signs with the keystore named by `DEMOLITION_KEYSTORE` / `DEMOLITION_KEYSTORE_PASS` / `DEMOLITION_KEYALIAS` / `DEMOLITION_KEYALIAS_PASS` (unset: debug-signed, Play refuses it). Release builds shrink Java with R8 in full mode; `Assets/Plugins/Android/proguard-user.txt` (Player Settings ▸ custom proguard file) holds the rules the ads SDK needs: without them the build fails, or the app closes at launch (WorkManager's Room database). A development build doesn't shrink, so check a release build on a phone.

**WebGL on itch.io:** Tools ▸ Demolition ▸ Build ▸ WebGL to itch.io (`Assets/Editor/Itch/ItchUpload.cs`): pushes `Builds/WebGL/` to the `html` channel with butler, building first unless `Builds/WebGL.stamp` matches a hash of `Assets/`, `Packages/`, `ProjectSettings/` and the Unity version. Butler is installed by hand and logged in once (`butler login` or `BUTLER_API_KEY`); the project (`user/game`) is kept per user in `UserSettings`. After the first push, mark the upload as playable in the browser on the itch.io project page.

**PlayMode tests** (`Assets/Tests/PlayMode/`): `BotRunTests` plays every campaign level to the finish with the `BotPilot` at 3x speed (minutes; editor only): `BotFinishesLevel` invincible (the level under test), `BotSurvivesLevel` mortal with the bot footage's upgrades and each action in turn (the bot under test). `RankedBotTests` plays them as ranked runs, solo and with two bots, firing a different action per level, fails when the server's verifier turns a log down, and saves the logs in `Temp/RankedLogs` for `RealLogTests` (`dotnet test` in `server/ranked`), which replays them on the server's runtime and tries every cheat on them. `ShotRunTests` plays every Clip Lab shot (bar `broll-*`) to its end and fails on steps that timed out.

Only the pure models have fast automated tests; everything physics/visual is verified manually in `Assets/Scenes/Sandbox.unity` (a `DemoBootstrap` test bench that builds ground, a building, player, camera and HUD entirely from code) or in a generated level (Tools ▸ Demolition ▸ Level Lab ▸ Play / Play with bot).

Build scenes (enabled): MainMenu → Tutorial → Level. The only other scene is the `Sandbox` test bench.

## Assemblies and the dependency boundary

- `Assets/Scripts/Demolition/Demolition.asmdef` → assembly **`Demolition`**: the destruction system, players, the run loop, its HUD. References `Unity.InputSystem`, `Unity.TextMeshPro`, `UnityEngine.UI`. Any other package used from this folder must be added to the asmdef's `references` or it won't compile (even though Assembly-CSharp sees it).
- Everything else in `Assets/Scripts/` (Menu) → **Assembly-CSharp**, which references `Demolition` — never the reverse. Menu choices reach the run through `Demolition.Run.Session` (joined devices) and `Demolition.Levels.LevelSelection` (which level).
- Feature folders inside `Demolition`: `Building`, `Generation` (buildings), `Level` (levels, M3), `Run`, `Player`, `Input`, `Pickup`, `Actions` (the crew's special moves), `Ranked` (ranked runs: the run log, its seal, the rules and the verifier the server replays a log with, `docs/ranked.md`), `Meta` (profile, shop, settings, level select), `Ads`, `Common`, `Sandbox`, `Clips` (the Clip Lab's shots).
- `Lighting/View/` is its own asmdef, **`Demolition.Lighting`** (references Demolition and URP; `defineConstraints` + `versionDefines` make Unity compile it only once `com.unity.render-pipelines.universal` is installed). `SceneLighting` adds itself to every scene: a global `Light2D` ambient (the run's `LevelTheme` light fields, else white), a global `Volume` with a code-built profile (bloom, vignette, colour adjustments), point lights on lamp/sign decor (`LevelBuilder.DecorSpawned`) and players' headlamps, a flash per `Dynamite.Exploded`; `GameSettings.effects` (Settings ▸ EFFECTS) turns all but a white ambient off. `RenderScaleView` hands `Meta.Quality.RenderScale` to the URP asset's render scale (in memory; restored when play mode ends). unity-check compiles it against `tools/unity-check/UrpStubs.cs` (URP 17.4 signatures from Unity-Technologies/Graphics `6000.4/staging`; URP isn't on the registry since Unity 6): add any new URP member you use there, copied from that source.

Players are located at runtime **by GameObject name** `"Player_1"` / `"Player_2"` (`RunController`, `SceneLighting`, `RunNet`) — scene references to players are not serialized, so keep those names.

## Run loop

`Scripts/Demolition/Run/`, one `Prefabs/Run/Run.prefab` per level (placed in Tutorial; instantiated by `LevelBootstrap` in the Level scene). The prefab carries `RunController`, `RunHud`, `ResultsView`, `PauseController` + `PauseView`, `TouchControls` and `RunJuice`:
- **Model:** `RunState` (countdown → playing → finished/failed; out-of-bounds grace, co-op free rejoin then Resurrect, finish + last call), `RunScore` (material points, collapse chain multiplier, speed bonus vs par, grade by level-wide destruction; players see the grade as 0–3 stars at 40/60/80%, finished runs only, saved as `LevelRecord.bestGrade`; a finish within par turns them rainbow (`Common/View/RainbowTint`; the HUD's while on pace, its par red once passed; saved as `LevelRecord.bestParGrade`, so the level select can show 2 rainbow + 1 gold)), `Objectives` (the job sheet: three bonus objectives per generated level, picked from its seed or pinned in the spec's `objectives`, judged at the bank from a `RunTally` (hits landed with weapons (`PlayerCombat.WeaponHits`, in the online kit), dynamite thrown, damage taken, the biggest collapse with its crumbles within 3 s) that the host keeps and sends in the `State` snapshot; FISTS ONLY forgives `FreeWeaponHits` (2) but no dynamite; each pays `CashEach` once, saved as `LevelRecord.objectives`; shown in the level select, the pause menu and the results through `JobSheetText`; `LevelGenerationTests` checks every level can do the chain job), `Session`.
- **Controller:** `RunController` finds the players, feeds the models (viewport out-of-bounds, finish crossing, health depletion, `DestructionEvents`) and applies their decisions (`PlayerHealth.Kill/Revive`, controls on/off, camera targets). Generated levels start on the move (`RunIn`, called by `LevelBootstrap`, not for Clip Lab shots): the players spawn back over the start's run-up (the countdown in the starting boots, within `LevelGrammar.RunUp` columns of street left of the spawn; online too, so nobody is seen at the spawn first) and a `ScriptedInputSource` runs them in during the countdown, holding right while they're behind schedule, so they reach the spawn at GO at full speed and the controls take over mid-run; the Tutorial starts standing. `FinishLine` marks the finish (placed by `LevelBuilder` in generated levels, by hand in Tutorial). `TutorialPrompt` markers (on the ground) each start a stretch of the tutorial: its sign (`TutorialSigns`, drawn by `RunHud` at world positions; `TutorialTrail` model) travels over the front player through that stretch and then stays on a striped post at the next marker. The message's first line is the heading; `{MOVE} {JUMP} {HIT} {TNT} {ACTION} {SWAP} {ZOOM} {PAUSE}` become the buttons of the devices the players have used (`InputGlyphs`). `nextScene` on the run enables the results screen's NEXT.
- **View:** `ScrollCamera` on `Main Camera 1` (full screen, no letterbox; push/auto-scroll, zoom framing anchored at the ground and the left edge (zooming out only widens ahead and up, never behind) that lowers to show floors below the street in view or just ahead via `LowestGround`, the players' own zoom on top (`Zoom`: mouse wheel / right stick / pinch through `PlayerInputFrame.Zoom`, 0.8–1.5×, kept across levels, never cropping a target; off with `GameConfig.playerZoom`), applies `CameraShake`), `RunHud` (drawn over the level: the timer, par and demolition meter in the middle, the meter lighting a star at each threshold; a steel panel per player in its top corner, P2 mirrored: crew tag, score, a slot for the weapon in hand with its hits left and one for the TNT; the fist icon is `Resources/UI/Fist`) and `ResultsView` (uGUI built in code through `UiFactory`; a skippable reveal: title slam, meter fill lighting up to 3 stars with chimes, count-ups, record stamp; NEXT / RETRY / SHOP / MENU, the shop opening over the results; the rewarded "2x cash"), `PauseView`, `RunJuice` (shake by collapse size, hit-stop, dust), `FinishLineView`.
- **End of run:** `RunController.Bank()` records the run in the profile (`SaveData.RecordRun`: cash, best grade/score/time, first clear) once the phase is Finished/Failed. `LevelId` is the spec id for generated levels, else the scene name. The Tutorial's first finish also pays `Economy.StartingCash` (2,500, once: `RunReward.StartingCash`), and `ResultsView` then opens `StartingCashView`, which says what the shop sells and where it is (OPEN SHOP / LATER).
- Pickups: `Scripts/Demolition/Pickup/` (`Pickup`, placed by `LevelBuilder` from the layout or by hand in Tutorial; `PickupView`), prefab `Prefabs/Pickups/Pickup.prefab`. Resurrect calls `RunController.Current.TryResurrect`.
- Score attribution: `TakeDamage(amount, instigator)` carries the player index (`PlayerInputReader.PlayerIndex`, assigned by the run). Collapsed blocks are credited to whoever destroyed the support; blocks credited once never score again. `PlayerHealth.ManagedByRun` makes depletion raise `Depleted` instead of the test-bench respawn.

## Levels (M3)

`Scripts/Demolition/Level/` (roadmap §5.2), content in `Assets/Content/<Theme>/Levels/*.json`:
- **Model:** `LevelSpec` (JSON: id, name, theme, seed, scrollSpeed, parTime 0 = auto (`LevelLayout.ParShare`, 55%, of the camera's auto-scroll time to the finish), pacing tokens `start street cluster:n terrace:n islands:n yard:n tower gap hill plateau sewer gate breather finish` (`cluster:n` is a row of different buildings wall to wall; `terrace:n` one archetype at one pinned size (`BuildingArchetype.Pinned`), so the roofs make a continuous run; `islands:n`: a pit and a landing strip between buildings; `yard:n`: n breakable props in a row on the street; `plateau`: a building on high ground), pickup budget (weapons spawn just before a building), allowed archetypes, `props` (breakable street props: crate, car, barrel, container; empty = the first three)) → `LevelGrammar.Generate` → `LevelLayout` (ground height per column, `NoGround` = pit, building placements each a validated `BuildingSpec`, pickups, spawn, finish, segments). Street dressing comes last from its own random stream (it never changes the course): props are tiny one-block buildings in `LevelLayout.Buildings` (`BuildingPlacement.IsProp`, archetype `prop.*`; damage, score, the meter and online sync work as for buildings; gas tanks go off through `Dynamite.Detonate` with `GameConfig.dynamitePrefab`, cosmetic on an online client), kept off doorsteps, the start and the finish; `LevelLayout.Decor` is cosmetic (`DecorKind` lamp, fence, bush, bin, sign; a fence along short stretches between buildings), drawn by `LevelBuilder` from the theme's `decor` sprites at sorting order -1. The crew's caravan (the Tutorial's trailer, `GameConfig.caravan`, the same in every theme) is parked just past the finish on `LevelLayout.CaravanX`, scaled to `CaravanWidth` columns the dressing keeps clear. `TraversalValidator` replays the player's jump (`JumpProfile` = `PlayerMotor` + prefab Rigidbody2D tuning) and rejects steps/pits a player can't clear; the grammar re-rolls derived seeds until it passes. `Daily` = one seed per date. Pcg32 only — same spec, same level.
- **Controller:** `LevelBootstrap` (the Level scene's only object) builds the selected level: camera, backdrop, players named Player_1/Player_2, `LevelBuilder`, the Run prefab (`Configure(id, par, plannedCells, next)`), music. `LevelBuilder` lays the ground tilemap once (a lit back wall behind trenches, near-black below pit lips plus hazard-striped pit edges, so a drop with a floor never looks like a pit) and streams segments (buildings via `BuildingBuilder`, pickups, finish) in ahead of the camera and out behind it. `LevelSelection` holds the chosen campaign level or daily across the scene load. `GameConfig` (`Resources/GameConfig.asset`) lists prefabs, scene names and the campaign's `LevelTheme`s in order; a theme (`Content/<Theme>/<Theme>Theme.asset`) has ground tiles, building tileset, archetypes, levels, sky, music and its backdrop layers (`BackdropLayer`: the sky gradient and three tiled silhouettes, plus a `single` sun or moon that rides with the camera at `offset` right of it; above the first layer, the sky, a cap in `theme.sky` carries it on however far the view zooms out, lit as the sky is, which the camera's clear colour isn't).
- Gates (`gate` token) use `DestructibleBuilding.CrumbleDetached`: knock out the wooden footing and the wall turns to dust instead of piling up in the street.
- Tools ▸ Demolition ▸ Level Lab previews a spec + seed, validates seeds, plays it (optionally with the bot); `LevelLab.ValidateAllCli` for batch mode.

## Clips (store media)

`Scripts/Demolition/Clips/` and `Assets/Editor/Clips/` (`docs/store-media.md` §3): **Tools ▸ Demolition ▸ Clip Lab** previews and records the shot files in `content-work/shots/*.json` with the Unity Recorder (`com.unity.recorder`; asmdef **`Demolition.Clips.Editor`**, compiled only once it is installed) into `content-work/media/raw/<shot>/take<n>.mp4` (on Linux the Recorder has no H.264: VP8 WebM, which ffmpeg turns into the MP4 in the background; `Status()` counts them), with the take's event log `take<n>.json` and stills. From agents through the Unity MCP: `ClipLab.Record(id, takes)`, `RecordAll()`, `Preview(id)`, `Status()`, `Stop()`, `Still()`, and `RecordTake(name, w, h, fps)` / `StopTake()` for whatever plays (a run by hand, online play). A take records at a fixed step: at 1080p60 the game runs at about a quarter speed while it records; at 960×540 30 fps with `Application.targetFrameRate` about 34 the editor keeps real time, which online play needs.
- **Model:** `ShotSpec` (level, building index, start offset, kit (upgrades, dynamite, weapon, the `actions` loadout, `charged`), camera `frame`/`pan`/`follow`/`run`, frame size, takes, and steps in lanes: 0 the director (`wait`, `slowmo`, `still`, `end`), 1–2 the players (`walk`, `hit`, `tnt`, `jump`, `back`, `swap`, `wait`, `bot`); `until` `collapse`/`break`/`blast`/`over`; times in video seconds), `ShotLog`, `ShotPlanning` (`WeakPoint`: the ground-level block whose loss brings down the most, as `BuildingValidator` judges it; `Frame`: a square master keeps the subject in its middle 9/16 so every crop holds it).
- **Controller:** `ClipDirector` (editor only, `#if UNITY_EDITOR`): boots from the Clip Lab's `PlayerPrefs` request before the Level scene loads, on a temporary profile (the shot's upgrades, no music); places and drives the players (`ScriptedInputSource`, walks through `BotPilot.StopX`), owns the camera (`RunController.IgnoreBounds` outside `run`), hides the HUD, sets the time scale (`RunJuice.BaseTimeScale`) and one physics step per frame (`fixedDeltaTime = timeScale / fps`); `Ready` after the countdown, the Clip Lab starts the Recorder and calls `Roll()`. `LevelBootstrap.Players` spawns two players for co-op shots.

## Actions

`Scripts/Demolition/Actions/`: the crew's chargeable special moves. Each player carries one into a level (the loadout) and fires it once its meter is full.
- **Model:** `ActionCatalog` (`ActionKind`; `ActionInfo`: id = its sprites' name, meter charge, seconds per frame (`UntilLanded` holds one until the player lands), the strike frame, a held loop, an effect duration, a price; the loadout in `SaveData.actions`, P1 first, the burp by default and free, the rest bought with cash (`SaveData.ownedActions`; `Equipped` falls back to the burp for one not owned)), `ActionMeter` (a destroyed block's cells, a collapse's cells times the score's chain multiplier; drains after 4 s without a point unless full).
- **Controller:** `ActionUser` on each player (added by `RunController.FindPlayers`, `RunController.Player.Action`): on `PlayerInputFrame.ActionPressed` ([C] or the middle mouse button, (Y), touch ACTION) with a full meter it takes the controls (`PlayerInputReader.Suppressed`), plays its frames on the player's sprite with the Animator off, and strikes at its strike frame through `ActionStrikes`: the burp (`BurpWave`: a band at chest height that wrecks any material and blows the debris on), the butt slam (straight down through the floors under the player), the crane (`CraneCall` marks the spot, `CranePallet` drops and smashes up to three times), controlled demolition (`ImplosionCharges`: the next building's footing, 3-2-1, `Dynamite.Detonate`), the coffee, hi-vis vest and shovel lean (buffs in `ActionUser`; the lean boosts the partner), the intern (`Intern`: a smaller copy on the player's animator, its punches the clip's `applyDamage` events) and the site radio (`SiteRadio`: pulses that burst glass, rattle walls and make rubble jump). Standing blocks only take damage (`TakeDamage`), never forces; debris is pushed with `BuildingBlock.Shove`, which wakes rubble. What a player's own action breaks doesn't charge their meter. A `TutorialPrompt` with `chargesAction` fills the meter of players passing it (the Tutorial's Prompt 70). To try them all: in the editor and development builds `ActionTestKeys` (added by `RunController`) gives Player 1 action 1–9 (catalog order) with a full meter on the number keys, Player 2 with Shift; then the action button.
- **Online:** `NetRole.ActionEvent` → `DM.Act`, one `ActionCall` (`NetPacking.PackAction`). The host decides everything the players share: it keeps both meters (its own count of who destroyed what, sent to the client 4× a second; the client never charges), lets an action start and strike once (`ActionGate`: a full meter, one at a time, the strike within 6 s and within 4 units of where the host sees the player) and picks what the strike hits (`ActionStrikes.Pick`: the charges' blocks, the radio's and the pallet's spot), runs it for real and sends the picks. The client says what its player carries (`Kind`), asks to start (`Start`; it plays its frames at once and stops them on `Deny`) and says where its player struck (`Strike`); it runs the host's `Struck` as the show, whose damage reaches it as cells. `ActionCall.Sendable` drops any phase the sender's role may not send. Buffs apply on the device that owns the player. Rule for new actions: whatever a strike chooses in the world goes in `Pick`, never in `Run`.
- **View:** `ActionSprites` (`Resources/Actions/P1|P2/<id>_<n>` and the props `pallet`, `radio`, `note`, made by `tools/artpipe/action_frames.py` from the poses in `content-work/actions/`; P2 is P1 recoloured with its stop sign), `ActionGlow` (a buff's outline), `FxRise` (steam, notes), `ActionAudio` (every action's sounds, timed to its frames in `ActionUser.Sounds` and played on both devices online: Freesound recordings in `Resources/Sounds/Actions/<name>.ogg` (CC0 / CC BY, sources and processing in `content-work/sounds/sources.md`, each in `Credits.txt`), the radio's 8 s 120 bpm music on its own voice; a missing file falls back to its `SynthSound` (`Burp`, `Whistle`, `Sweep`, `Noise`, `Clang`), a missing `Radio.ogg` to the synth tune; the slam's rumble and the buffs' power-up are synth only), the action bar in each HUD panel, `ActionsView` (the loadout, from the shop's ACTIONS).

## Meta, menus and ads

- `Meta/`: `SaveData` (model: cash, `LevelRecord` per level id, upgrades, `GameSettings`, ad counters) persisted by `Profile` (JSON in `persistentDataPath/profile.json`). `UpgradeCatalog`/`Economy` (models) define the skill shop; `LookCatalog` (model) the crew's look items (looks only; bought with cash, earned with full job sheets, or the supporter's that come with REMOVE ADS; owned in `SaveData.looks`). Each item dresses one `LookSlot`: OUTFIT (trousers and shoes), SIGN (recolours the player's own sign, or puts another traffic sign on: `LookInfo.Head`), CHAIN, BRACELETS, TATTOO. A player wears one item per slot, any mix (`SaveData.dressed`; `Wear`/`TakeOff`/`Wearing`), and `LookCatalog.Combine` puts them together as one look. The items are `Resources/Looks.json`, loaded by `AppBootstrap`. Colours change by `LookPalette.Map` (the source colours of P1's and P2's sheets; skin and weapons never change); the chain, bracelets, chest eagle and arm hearts come by `LookPalette.Extras` from one overlay per sheet and action frame, `Resources/LookOverlays/P1|P2/<texture>`. `tools/artpipe/accessories.py` draws those in key colours from the spots per frame in `content-work/looks/anchors.json` (review: `content-work/looks/anchors.png`). The overlays also mark the player's own sign (cleared for another one) and what no look recolours though it's drawn in a look's colour: the radio, the skin's yellow highlights, the clipboard and shovel handle in the shoes' brown, the detonator, the sign's mark. ## Destruction architecture (support-graph)

Three layers; read `docs/building-destruction-design.md` for the why.

1. **`Building/Model/BuildingStructure.cs`** — pure C#, no MonoBehaviour/physics. Cells on an integer grid, anchors, 4-neighbour flood-fill from anchors. `RemoveCells()` returns every cell that lost its path to ground. `ComputeStress()` is a two-pass heuristic (carried cells → cantilever/span/hanging, then pillar columns sum load and moment) that yields per-cell `Stress/Lean/Drift/Overload`. Fragile cells (glass) are held by neighbours but support never flows through them and they carry no load.
2. **`Building/Controller/DestructibleBuilding.cs`** — owns one structure plus the live blocks. On `OnBlockDestroyed` it removes the block's cells, calls `BeginFalling()` on detached blocks (capped by `maxSimultaneousFalling` and the quality tier's `FallingLimit`; overflow is destroyed without simulation), then recomputes stress. A stress **baseline** captured at `Start` is subtracted so intact buildings show no strain. Supports overloaded past baseline + `overloadTolerance` take crumble damage in `Update`, through the normal `TakeDamage` path.
3. **`Building/Controller/BuildingBlock.cs`** — per-block lifecycle: **Static** while supported → **Dynamic** while falling (strips any leftover `Joint2D`, hurts a player it comes down on head first (within `maxImpactAngle` of straight down; landing on it or running into it does nothing), takes self-damage on hard landings, glass shatters on contact) → **Static rubble** once settled. Rubble is outside the support graph, so a block that is destroyed, vanishes or starts falling wakes the rubble resting on or wedged against it (`WakeRubbleAround`), which falls again until it re-settles.

Invariants to preserve:
- Every damage to a standing block names its cause: `TakeDamage(amount, instigator, HitCause, from)` (`Ranked/Model/RunLog`). A ranked run logs it (`RunRecorder`) and the server holds it to that cause's rules (`docs/ranked.md`); a new way to damage a standing block needs its cause there and in `RunVerifier`, or ranked runs that use it are turned down.
- Standing blocks stay `RigidbodyType2D.Static`; only detached debris is ever dynamic. Don't add forces/joints to standing structure — this is the core perf/stability decision.
- Stress lean/sag/tremble is **cosmetic only**: it moves the `Visual` child transform holding the sprite (migrated there at `Awake`), never the root/collider. Collapse decisions come only from connectivity + overload crumble.
- Damage tint darkens RGB only and is monotonic; alpha is never touched.
- Keep structural decisions discrete and deterministic inside `BuildingStructure` — the planned NGO netcode replicates destroyed-cell sets, not rigidbodies.

### Building authoring contract (hand-made prefabs)

Building prefab roots (`Prefabs/Buildings/`, `Sky's Prefabs/`) carry a `DestructibleBuilding` with `autoScanChildren` on. Wall segments in `Prefabs/Building Materials/` deliberately do **not** — each `BuildingBlock` belongs to its nearest ancestor `DestructibleBuilding`.

At `Start`, if nothing registered blocks in code, the building auto-scans children:
- Each block's world AABB (from collider geometry, not stale `Collider2D.bounds`) is rasterized onto a `cellSize` (1 unit) grid relative to a shared origin; multi-cell footprints (beams, platforms) occupy several cells and detach as one rigid unit.
- Foreground and larger blocks claim cells first; blocks whose **name contains "bg"** sort last. A block whose cells are all already claimed becomes a cosmetic **rider** of the overlapping host — no structural role, falls when the host goes.
- Other sprites under the building with no script between them and the root (a flame on a chimney) are **dressing** of the block they sit on: their solid colliders and rigidbody are switched off, and they go out in a puff of smoke when that block leaves the structure.
- Anchors: blocks with a non-block, non-dynamic, non-trigger collider within `anchorProbeDepth` below them. If none touch ground, the lowest row is anchored.
- Cells with no path to an anchor at `Start` (a block that doesn't touch the rest) fall right away, with an editor warning naming the block, instead of hovering until the first hit.
- `BlockMaterial` (Brick/Metal/Wood/Glass/Support) sets default health; Glass registers as fragile.

Code-driven alternative (`DemoBootstrap`): call `BuildingBlock.Initialise` + `DestructibleBuilding.RegisterBlock` before the building's `Start`, which then skips the scan.

Joints exist only outside the standing structure: `HangingChain` makes them in code for chains and plank walkways (the Tutorial's `Tall Bridge` deck and its two chains): at Start it hinges its child links to each other and to their anchors (a pillar's block, or a pin in the world) and makes them dynamic; it moves itself out of the building at Awake so the scan doesn't adopt them. The links keep an unregistered `BuildingBlock`, so hits and blasts break them, and an end whose anchor block is destroyed drops.

## Building generation

`Scripts/Demolition/Generation/` (see `docs/roadmap.md` §5.1):
- `BuildingGrammar.GenerateValid(archetype, seed, out report)` → `BuildingSpec` (blocks on a cell grid, bottom-left (0,0), ground row anchored). It retries derived seeds until `BuildingValidator` says the building stands and has the archetype's weak-point count. Same seed, same building (`Pcg32`, never `UnityEngine.Random`, inside the grammar).
- Glass carries nothing, so walls with windows hang from the slab above; interior `Support` columns (walk-through triggers) are the backbone. Stairwells never cut a slab piece off from them.
- `BuildingBuilder.Build(spec, tileset, origin)` registers cells in code at runtime; in edit mode it only creates the objects, and a baked prefab auto-scans to the same cells.
- Archetypes are JSON in `Assets/Content/<Theme>/Archetypes/`; looks come from a `BuildingTileset` asset (`TownTileset`). Block visuals sit on a child `Visual`; `BuildingBlock` keeps its authored rotation/scale/offset under the stress lean. A tileset entry's `left` / `right` sprite lists dress the blocks on the building's silhouette (`BuildingSpec.EdgeOf`: the outermost block of every row it spans) with the theme's corner trim; the plain `sprites` serve the rest. Variants are picked by the block's random `Variant`.
- Back walls: `BuildingSpec.Interior()` lists the open and see-through cells inside each row's outermost blocks and every window cell (outer walls too; a window hangs from its lintel, so a broken one shows the room), with the storey each is on (counted up at every floor-slab row); `BuildingInterior` (built by `BuildingBuilder` when the tileset has an `interior` sprite) draws one cosmetic sprite per cell at sorting order -1 (`BuildingTileset.InteriorFor`: the base look and `interiorVariants` in turn per storey, from the building's seed) plus an `interiorDetails` sprite on some open room cells (`CellHash`, mirrored by `level_preview.py`), and destroys them when the cell they hang from leaves the structure (`DestructibleBuilding.CellsRemoved`).
- Building Lab: Tools ▸ Demolition ▸ Building Lab. From agents: `BuildingLab.Validate(path, seeds)`, `BuildingLab.RenderContactSheet(...)` (PNG in `Temp/`), `BuildingLab.ValidateAllCli` for batch mode.
- The validator judges with `StructureDefaults` (the `DestructibleBuilding` defaults). A building whose serialized tuning differs plays differently from what the validator predicted.

## Code structure (MVC)

The project follows Model–View–Controller. Keep the structure clean: no person-named folders, no scratch files in `Assets/`, delete dead code instead of leaving it around.
- **Model** — plain C# state and rules. No MonoBehaviour, no scene access, unit-testable in EditMode. Example: `Building/Model/BuildingStructure`.
- **View** — MonoBehaviours that only present: sprites, animation, HUD, particles, audio, camera framing. They read models or listen to events and never change game state.
- **Controller** — MonoBehaviours that turn input and events into model changes and tell views what to show. Example: `DestructibleBuilding`.
- Folders go feature first, then layer: `Scripts/<Feature>/Model|View|Controller/`. New code uses this layout; existing scripts move into it (with their `.meta`) when a milestone touches them. Don't restructure untouched code.
- Legacy exception: the person-named `Prefabs/Sky's Prefabs/` holds two of the Tutorial's hand-made buildings and stays while the Tutorial does.

## Unity conventions here

- Input System supported devices (`Assets/Prefabs/InputSystem.inputsettings.asset`) must include `Mouse` and `Touchscreen`, or UI clicks, mouse attack and every touch control silently do nothing.
- Unity 6 physics API: `Rigidbody2D.linearVelocity` / `linearDamping` (not `velocity` / `drag`).
- Platforms: PC (keyboard/gamepad), TV (gamepads, 10-foot readable HUD), phones/tablets in landscape (touch). UI built in code goes through `UiFactory` (1920×1080 reference with `Expand` matching, so the whole reference rect is on screen at any aspect; `SafeArea` for edge-anchored HUD, `Canvas(scale)` for bigger UI, `EnsureEventSystem` adds an Input System UI module). Every menu must work with mouse, gamepad navigation and touch.
- UI look: `UiFactory` holds it. `DisplayFont` is Black Ops One (SIL OFL, `Resources/Fonts`) turned into a dynamic TMP font at runtime; `Outline`/`Heading` materials only use keyword sets the bundled TMP materials already use (outline; outline + underlay), so the shader variants ship. `Button` is a riveted steel plate (steel, gold when selected) with `UiButtonFeel` (grows when selected, ticks and clanks through `UiAudio`); `Panel` puts a plate with a hazard strip behind an overlay, `TitledPanel` adds its title on a dark nameplate across the strip (gold on the yellow stripes is unreadable); `Title`, `Stripe`, `Star`. The sprites in `Resources/UI` come from `tools/artpipe/ui.py` (pixel art, 25 PPU = 4 UI units per pixel).
- When creating, moving or deleting assets from the filesystem, move/delete the matching `.meta` file too — prefabs and scenes reference scripts by the GUID in it.
- Commit messages use conventional prefixes (`feat:`, `fix:`, `docs:`).
